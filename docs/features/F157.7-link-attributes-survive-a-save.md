# F157.7 — Et link mister `target` og `rel` når feltet omkring det redigeres

**Status:** backlog · **Parent:** [F157 Inline Editing](./F157-inline-editing.md) · **Målt:** 2026-08-25 på broberg.ai

## Hvad der sker

En byline indeholdt et håndskrevet link. Der blev rettet i en HELT anden sætning i samme felt, og efter gemningen så værdien sådan ud:

```
FØR:  … af <a href="https://www.instagram.com/uxgoodies/" target="_blank" rel="noopener noreferrer">@uxgoodies</a> på Instagram.
EFTER: … af [@uxgoodies](https://www.instagram.com/uxgoodies/) på Instagram.
```

Linket virker stadig. Men det åbner ikke længere i en ny fane, og `rel="noopener noreferrer"` er væk — og dét er en sikkerhedsattribut, ikke pynt: uden den kan den side man linker til nå tilbage i den fane man kom fra.

## Hvorfor

Serialiseringens `<a>`-gren beholder kun attributterne når linket bærer `data-cms-ref` (en F164-sidehenvisning). Alt andet bliver til `[tekst](adresse)`, og Markdown har ingen plads til resten.

Ingenting fejler, og ingenting advarer. Det er den slags tab man først opdager når nogen spørger hvorfor linket holdt op med at åbne i en ny fane.

## Rækkevidde

Gælder hvert site på pakken, og hvert felt hvis værdi er skrevet med rå HTML — hvilket er normalt for indhold der er skrevet før inline-redigering fandtes.

## Retningen

Behold linket som rå HTML når det bærer andet end `href` (samme greb som `data-cms-ref` allerede bruger), og lad et helt almindeligt link blive Markdown som i dag. Markdown-gengiveren viser rå inline-HTML, så begge former overlever visningen.

## Bevis

Se acceptkriterierne. Kernen: læs værdien tilbage fra serveren og sammenlign selve link-markupen med streng lighed — "linket er der stadig" er ikke det samme som "linket er uskadt".
