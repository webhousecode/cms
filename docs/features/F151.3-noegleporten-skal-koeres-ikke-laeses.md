# F151.3 — Nøgle-porten skal køres, ikke læses

**Forælder:** F151 (Lens mint-endpoint)
**Status:** i gang
**Anledning:** cardmem intercom #22851, 27. august 2026

---

## Hvordan det kom frem

cardmem meldte en faldgrube de havde fundet i deres EGEN diff — ikke i kortet,
og ikke hos os:

```js
const secret = opts.secret ?? process.env.LENS_MINT_SECRET;
```

Giver man `@broberg/lens` en skrive-hemmelighed der er usat på det tidspunkt,
bliver `opts.secret` undefined, og pakken falder tilbage til **læse**-hemmeligheden.
Skrive-porten autentificerer så mod den svage nøgle: hullet er præcis lige så
stort som før opdelingen, men nu med et lukket kort ovenpå.

De foreslog en konkret prøve: *unset skrive-nøglen og se om læse-nøglen pludselig
virker på write-mode.*

## Hvad målingen viste

**Vores form er rigtig.** `resolveLensKey()` læser begge hemmeligheder direkte
og pr. request:

```ts
const read  = process.env.LENS_MINT_SECRET;
const write = process.env.LENS_WRITE_SECRET;
if (write && bearer === write) return "write";
```

Der er intet `??` at falde igennem. Er `write` usat, matcher grenen aldrig, og
en skrive-anmodning ender på 403.

Deres **andet** fund rammer os heller ikke: rækkefølgen i handleren er
401 → 400 (`writes:true`) → 403 (forkert nøgle) → **først derefter** log-linjen,
så `writeSession` kan kun være sand efter alle tre porte. En afvist,
skrive-formet request efterlader ingenting. Det var dog held snarere end
fremsyn — opustnings-retningen havde jeg ikke tænkt på før de skrev den.

## Men det er ikke det testene beviser

```ts
const fn = mint.slice(mint.indexOf("function resolveLensKey("));
expect(fn).toContain('if (write && bearer === write) return "write";');
```

Det er en assertion om en **tekststreng i en fil**. Den:

- går grøn på enhver refaktorering der flytter resolveren ud i en hjælper
  **med** faldgruben i,
- ville være gået grøn på `@broberg/lens`' egen fejl, hvis vi havde skrevet
  koden i den form,
- kan altså ikke skelne netop den fejl den er skrevet imod.

En prøve der ikke kan skelne sin egen fejl er ikke dækning — det er en
kommentar der ser ud som en test. Og den er farligere end ingen test, fordi den
får en læser (mig, i går) til at svare "det gælder ikke os" med større
sikkerhed end grundlaget bærer.

Det er samme familie som husets egen erfaring med `toContain`: en svagere
prædikat end den læser som, og den fejler i den **grønne** retning.

## Hvad der bygges

Ruten er let at køre — den importerer kun `next/server`, `jose` og vores egen
`dev-jwt-secret`. Registry-opslaget er dynamisk og nås kun når body bærer
`org` + `site`, så en prøve uden dem rører intet filsystem.

Så: konstruér en `NextRequest`, kald `POST`, dekod den JWT der kommer ud, og
døm på claims.

| Tilfælde | Forventet |
|---|---|
| skrive-nøgle **usat**, læse-nøgle beder om write | 403, ingen `lensWrite` nogen steder |
| begge sat, læse-nøgle beder om write | 403 |
| begge sat, skrive-nøgle beder om write | 200, `lens:true` **og** `lensWrite:true` |
| begge sat, skrive-nøgle beder **ikke** om write | 200, `lens:true`, **ingen** `lensWrite` |
| `mode:"write"` uden `writes:true` | 400 |
| begge variabler sat til samme værdi | afvist |
| flere afviste write-formede requests | præcis ét spor i loggen |

Den sidste række er cardmems tælle-pointe: en assertion pr. request går grøn
på netop det tilfælde der er forkert. Der skal tælles.

## Hvad der IKKE fjernes

Ikke alle kildescanninger er dårlige. Der hvor **filen selv er kontrakten** —
fx at `proxy.ts` overhovedet bærer write-guarden — er en scanning det rigtige
værktøj, og guard-testens egen "reads the files it thinks it reads"-kontrol er
netop det der forhindrer den i at scanne ingenting og melde grønt.

Reglen er snævrere: **alt der kan køres, skal køres.** De scanninger der
erstattes, **slettes** — to prøver for samme ting, hvor den ene er svagere,
læser som dobbelt dækning og er det modsatte.

## Risiko

Ingen adfærdsændring. Den eneste reelle risiko er at en ny prøve er lige så
vag som den den erstatter — derfor er mutation-tjek et krav pr. prøve, ikke
en afsluttende formalitet: bræk porten på én bestemt måde, og netop den prøve
skal gå rød.
