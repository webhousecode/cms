# F203.4 — Én fælles privatlivsside for Web House ApS

**Ordre:** Christian 29/9-2026 (via components) om de manglende privatlivssider: «They can manage that». Beslutningen er cms'.

## Beslutning
ÉN fælles side på www.webhouse.dk — dansk `/da/privatliv` og engelsk `/en/privacy` — som alle tre sites linker til via `privacy-href` på `<broberg-consent>`.

**Hvorfor én:** alle tre sites (docs.webhouse.app, www.webhouse.dk, webhouse.app) drives af samme dataansvarlige, WEB HOUSE ApS (CVR 21221198). Tre sider om samme firma ville drive fra hinanden; én side kan ikke sige noget andet end sig selv.

**Fravalgt:** at linke til broberg.ai/privatliv — den beskriver kun broberg.ai («ingen cookie-boks») og ville være usand om de andre sites.

## Arbejdsgang
1. **Mål først** pr. site: cookies (kun `broberg-consent` + evt. login-cookies på webhouse.app), formularer (webhouse.dk-kontaktformularen, F167), login (webhouse.app via Broberg ID), logfiler/hosting (Fly, arn), databehandlere (compliance/subprocessors.public.json fra F201). Ingen påstand på siden uden måling bag.
2. **Tekst i CMS** (husregel D-129cb4): webhouse.dk's indhold redigeres på webhouse.app; siden oprettes som dokument der, DA+EN med translationGroup, læst tilbage og fundet af søgningen.
3. **Rendering** i webhouse-site hvis ruten ikke findes; deploy fra ren kopi (repoet har andres ucommittede arbejde).
4. **Bannere**: `privacy-href` på alle tre, sprog efter side.
5. **Bevis**: Lens mod prod — siden svarer, «Læs mere» åbner den.

## Åbne spørgsmål
- Hvordan når CMS-indhold til webhouse.dk i dag (ICD-push fra webhouse.app til webhouse-dk-volumen, eller andet)? Måles i trin 2.
- Har webhouse.dk-kontaktformularen en virkende modtager (F167 siger «den leverer ingenting»)? Siden må kun beskrive hvad der faktisk sker.

## Reuse
`@broberg/consent-cookie` (privacy-href). Databehandler-listen fra F201 genbruges som kilde.
