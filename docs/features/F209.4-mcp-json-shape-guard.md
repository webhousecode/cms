# F209.4 — MCP-indgangen afviser for store lister før zod ser dem

## Hvorfor
Christian 24/10: «ja lav kortet og luk det helt og kør til Done».

GHSA-mrhx-c7xc-m3w5: zod laver ét fejl-objekt pr. forkert element. Målt 24/10 på zod 4.6.7: et `z.array` UDEN `.max()` på 2.000.000 forkerte elementer koster ~923 MB; med `.max(10)` 0 MB. Opgraderingen (F209.3) lukker altså kun lister med længdegrænse.

Den offentlige indgang uden login er `/api/mcp` (+ `/api/mcp/admin` med nøgle). Beskederne parses af MCP-SDK'ens egne skemaer, som vi ikke styrer. 256 KB-loftet (c0905523) rummer stadig ~128.000 elementer.

## Løsning
Tæl formen på den parsede JSON i `readJsonLimited` — før beskeden gives til SDK'en:
- højst 1.000 elementer i én liste
- højst 1.000 nøgler i ét objekt (`z.record` har ingen `.max()`)
- højst 10.000 i alt i hele beskeden

Overskrides én → 400 med stien. Iterativ gennemgang, så dyb nesting ikke sprænger stakken. Uafhængigt af content-type (grænsen tæller bytes og elementer, ikke headeren).

Grænserne er lavere end cardmems (20k/1k/200k), fordi en MCP-læse-klient sender små argumenter (et slug, en søgetekst).

## Reuse
`measureJsonShape` er porteret fra cardmem `apps/server/src/json-shape-guard.ts` (ff41e864). To kopier i flåden → components får besked om at det hører hjemme i en `@broberg/*`-pakke.

## Non-goals
- `.max()` på SDK'ens skemaer (ikke vores kode).
- Andre ruter: ingen af vores egne ruter parser netværks-input med zod.

## Rollout
Grøn port → udrulning → mål udefra (stor liste → 400, normal session → 202).
